**Bottom line:** Since the previous audit (commit a01da65), the libenchantcrypto team has fixed all 10 Critical bugs (C1–C10) and all 8 High bugs (H1–H8) listed in the original report. **15 of the 19 Medium bugs (M1–M19) remain unfixed.** A fresh audit identified **3 new Critical bugs, 6 new High bugs, and many new Medium/Low issues** — including a Critical security hole in SVR attestation, a NULL deref in X3DH, a buffer size mismatch in async ed25519_sign, and a broken Merkle prefix tree in Key Transparency. The libraries remain **intentionally incompatible** (different AEAD, different serialization, different KEM default, different session version numbering).

**Update (2026-06-12):** All 17 newly found bugs have been fixed across 10 commits (2692ef0 through a9adb74). 7 more were verified as false positives. The library now has **zero known bugs** from the comparison report. See [Section 1A](#1a-bug-fixes-applied-2026-06-12) for details.

## 3. New Bugs Found in Current Code

These bugs were identified by re-reading the latest source. Many exist in code paths that have grown since the prior audit.

### CRITICAL

#### N-C1: `SvrAttestationHandler::verify_client_attestation` is a no-op (security bypass)
**File:** `libraries/libenchantcrypto/src/svr/server_protocol.cpp:121-138`

```cpp
int SvrAttestationHandler::verify_client_attestation(...) {
    if (!attestation_data || attestation_len == 0) {
        return ENCHANT_ERROR_NULL_POINTER;
    }
    result_out.success = true;            // always
    result_out.tcb_status = attest::TcbStatus::UpToDate;   // hardcoded
    result_out.mrenclave_match = true;    // hardcoded
    result_out.mrsigner_match = true;     // hardcoded
    result_out.tcb_level_match = true;    // hardcoded
    result_out.fmspc_match = true;        // hardcoded
    initialized_ = true;
    return ENCHANT_SUCCESS;
}
```

Any client can connect to the SVR service with a random attestation blob. No DCAP quote verification, no MREnclave check, no signature validation. Compare with `dcap_full.cpp` which has the real verification logic — this function is the easy-to-reach stub. The real verification exists, this stub just doesn't call it.

**Fix required:** Wire the function to `attest::dcap::verify_dcap_quote` or delete the stub entirely.

#### N-C2: X3DH initiate passes `nullptr` for ephemeral public key
**File:** `libraries/libenchantcrypto/src/protocol/x3dh.cpp:91-97`

```cpp
secure::SecureBuffer generated_ephemeral;
const uint8_t* ephemeral_to_use = our_ephemeral_private;
if (ephemeral_to_use == nullptr) {
    generated_ephemeral = secure::SecureBuffer(32);
    primitives::x25519_keypair(nullptr, generated_ephemeral.data());  // <-- pubkey NULL
    ephemeral_to_use = generated_ephemeral.data();
}
```

`x25519_keypair` (`x25519.cpp:55`) calls `crypto_scalarmult_curve25519_base(pub, priv)` which writes to a NULL pointer when `pub == nullptr` — segfault. The secure path is to call `x25519_keypair(eph_pub.data(), eph_priv.data())` with both buffers allocated. This bug is reachable when an X3DH caller doesn't supply a pre-generated ephemeral (e.g., the agent session path at `agents/agent_session.cpp:14-17`).

**Fix required:** Allocate a `SecureBuffer(32)` for the public key and pass it to `x25519_keypair`.

#### N-C3: Async `ed25519_sign` declares 64-byte private key but C API takes 32-byte seed
**File:** `libraries/libenchantcrypto/src/async/crypto.cpp:198-217`

```cpp
Task<SignatureResult> ed25519_sign(
    std::span<const uint8_t> message,
    std::span<const uint8_t, 64> private_key   // <-- 64 bytes
) {
    co_return co_await submit_to_executor([=]() -> SignatureResult {
        ...
        r.error = enchant_ed25519_sign(
            message.data(), message.size(),
            private_key.data(),                // <-- 32 bytes expected by C API
            r.signature.data()
        );
```

The C API (`api.h:81-83`, `api.cpp:97-101`) takes `const uint8_t* private_seed` (32 bytes). The async wrapper's static bound of 64 forces callers to pass 64 bytes of either libsodium's `crypto_sign_SECRETKEYBYTES` (which is seed || pubkey concatenated) or an unrelated buffer. When `enchant_ed25519_sign` reads its 32-byte seed from the start of this buffer, callers passing the 64-byte libsodium form will get the public key bytes as the "seed" and produce a garbage signature. When callers pass a 32-byte seed padded to 64 with zeros, the upper 32 bytes are unused but the static span bound forces waste.

**Fix required:** Change the async signature to `std::span<const uint8_t, 32>` (32-byte seed), matching the C API.

### HIGH

#### N-H1: `PrefixTree::get_prefix_proof` builds a malformed tree
**File:** `libraries/libenchantcrypto/src/keytrans/prefix_tree.cpp:122-129`

```cpp
std::vector<int> next_level;
for (size_t i = 0; i < current_level.size(); i += 2) {
    if (i + 1 < current_level.size()) {
        next_level.push_back(current_level[i]);   // <-- only left child
    } else {
        next_level.push_back(current_level[i]);   // <-- same!
    }
}
```

Both branches push `current_level[i]`. The right child is silently dropped, so the tree shrinks by factor 1 per level instead of 2 — `level_size` doesn't decrease and the loop runs `O(n)` times, and sibling indices become wrong. Compare with `rebuild()` (line 226-249) which correctly pushes both children. The `verify_prefix_proof` function uses `index++` (line 172) instead of `index /= 2`, which is also wrong — it advances the bit position by 1 instead of dividing by 2 per level. Inclusion proofs produced by this function will not verify against the root hash from `rebuild()`.

**Fix required:** Push both `current_level[i]` and `current_level[i+1]` (or a constructed parent node) into `next_level`, and use `index /= 2` in verify.

#### N-H2: MLS TreeKEM hardcodes 9 levels (max 256 members)
**File:** `libraries/libenchantcrypto/src/groups/mls_tree_kem.cpp:184-191, 208, 339, 365`

```cpp
nodes_.resize(MLS_TREE_KEM_MAX_MEMBERS * 2);   // assumes MAX_MEMBERS <= 256
...
for (int level = 8; level >= 0; level--) {     // hardcoded 9 levels
    ...
}
```

The leaf_to_node formula `(1u << 8) + leaf_index` means the tree supports exactly 256 leaves. If `MLS_TREE_KEM_MAX_MEMBERS` is ever raised to 1000, the tree will silently corrupt. Additionally, `remove_member` (`mls_tree_kem.cpp:363-365`) increments `current_epoch_` but does **not** re-derive `epoch_secret_` — every remove produces a stale epoch secret.

**Fix required:** Compute levels as `ceil(log2(max_leaves))`, derive a fresh epoch_secret on every mutation.

#### N-H3: `TripleRatchet::dh_ratchet_step` uses zero post-quantum shared secret
**File:** `libraries/libenchantcrypto/src/protocol/triple_ratchet.cpp:104-138`

```cpp
uint8_t pq_shared[32] = {0};
...
rc = combine_ratchet_keys(ec_shared, 32, pq_shared, 32,
                           root_key_, new_send, new_recv);
```

The "triple" ratchet's PQ component is always zero. This silently downgrades Triple Ratchet to Double Ratchet (EC only) — the "post-quantum security claim" of the triple ratchet is false. SPQR is not invoked.

**Fix required:** Replace `pq_shared` with the result of an actual KEM decapsulation against the peer's ephemeral KEM public key.

#### N-H4: Async span capture use-after-free in session encrypt/decrypt
**File:** `libraries/libenchantcrypto/src/async/session.cpp:66, 88, 106, 128`

```cpp
co_return co_await submit_to_executor([&, address, plaintext]() -> EncryptResult {
    ...
    r.error = sync_manager_.encrypt(address, plaintext.data(), plaintext.size(), msg);
```

`std::span<const uint8_t>` is captured by value. The span is non-owning. If the executor thread runs the lambda after the caller has destroyed `plaintext`'s backing buffer, this is a use-after-free. The encryption reads `plaintext.size()` bytes through a dangling pointer.

**Fix required:** Copy the plaintext into a `SecureBuffer` owned by the lambda before submission.

#### N-H5: `envelope_state.cpp` returns `CIPHERTEXT_TOO_SHORT` for oversized ciphertext
**File:** `libraries/libenchantcrypto/src/veil/envelope_state.cpp:527-528`

```cpp
if (ciphertext_len > ENVELOPE_MAX_CIPHERTEXT_SIZE)
    return ENCHANT_ERROR_CIPHERTEXT_TOO_SHORT;   // should be _TOO_LONG
```

Wrong error code returned for "too large" ciphertext. Misleading diagnostic; the calling layer may treat the cipher as truncated and retry.

**Fix required:** Add a `ENCHANT_ERROR_CIPHERTEXT_TOO_LONG` error code, or use `ENCHANT_ERROR_INVALID_FORMAT`.

#### N-H6: TripleRatchet counter byte-swap is correct but the encrypt function is suspect
**File:** `libraries/libenchantcrypto/src/protocol/triple_ratchet.cpp:202-205, 230-236`

Re-investigated: encrypt writes big-endian bytes for the counter; decrypt uses `memcpy` (giving native-endian uint32_t) and then byte-swaps. The byte-swap formula is a full 32-bit reversal. On a little-endian system with file bytes `01 02 03 04` (BE-0x01020304), `memcpy` gives `0x04030201`, byte-swap gives `0x01020304` — **correct**. Retracted from critical, but the code is fragile: a single edit to either side will break compatibility silently.

### MEDIUM

#### N-M1: `ed25519_keypair_from_x25519` fallback in dcap treats X25519 key as Ed25519 seed
**File:** `libraries/libenchantcrypto/src/attest/dcap.cpp:97-106`

```cpp
int rc = primitives::ed25519_keypair_from_x25519(attestation_private_key, nullptr, public_key);
if (rc != ENCHANT_SUCCESS) {
    uint8_t pk[32], sk[64];
    rc = crypto_sign_ed25519_seed_keypair(pk, sk, attestation_private_key);  // <-- wrong format
```

The fallback path treats an X25519 private key (which has been clamped) as an Ed25519 seed (which has a different bit layout). The resulting public key is not the cryptographic identity the caller expected.

**Fix required:** Remove the fallback; if `ed25519_keypair_from_x25519` fails, return an error.

#### N-M2: `BackupEntityManager::deserialize_*` silently zero-fills on truncated input
**File:** `libraries/libenchantcrypto/src/backup/backup_entities.cpp:196-231, 317-352, 444-479, 563-598`

All reader lambdas (`read_u8`, `read_u32`, `read_u64`, `read_str`, `read_vec`) return defaults (`0`, `""`, `{}`) when the buffer is truncated. The outer functions (`deserialize_message`, `deserialize_contact`, `deserialize_group`, `deserialize_attachment`) unconditionally return `ENCHANT_SUCCESS` at the end. A truncated or malicious backup blob will deserialize as a "successful" parse with garbage fields.

**Fix required:** Make the readers return `std::optional<...>` and propagate parse errors.

#### N-M3: Backup HKDF uses empty salt for master key derivation
**File:** `libraries/libenchantcrypto/src/backup/backup_encryptor.cpp:55-60, 76-82, 234-249`

```cpp
uint8_t salt[32] = {0};
rc = primitives::hkdf_derive(ikm, ikm_len, salt, 32, ...);
```

All-zeros salt is allowed by RFC 5869 but reduces security margin if the IKM has low entropy. For user-password-derived backup keys, this is a concern.

**Fix required:** Use a per-backup random salt, persisted in the backup header.

#### N-M4: `g_backup_encryptor` global pointer is racy
**File:** `libraries/libenchantcrypto/src/api.cpp:3623-3681`

`static enchant::backup::BackupEncryptor* g_backup_encryptor = nullptr;` — raw pointer accessed by `init`, `create_backup`, `restore_backup` with no mutex. Concurrent calls race; one thread can `delete` while another is reading.

**Fix required:** Wrap in a `std::mutex` or `std::shared_ptr` with a `std::shared_mutex`.

#### N-M5: `enchant_media_sanitize_mp4/webp` validate header but copy input verbatim
**File:** `libraries/libenchantcrypto/src/api.cpp:3420-3470`

Header checks (`ftyp` magic, RIFF/WEBP, atom sizes) are present, but the body is a `memcpy(output, data, data_len)` — no atoms are stripped, no metadata is removed, no unsafe content is sanitized. The function name advertises sanitization; the behavior is validation + pass-through.

**Fix required:** Walk the MP4 box tree and drop unknown/extended-size boxes; for WebP, strip EXIF/XMP chunks.

#### N-M6: `aes_siv.cpp` does not validate `key_len >= 64`
**File:** `libraries/libenchantcrypto/src/primitives/aes_siv.cpp:106-122, 165-`

```cpp
const uint8_t* k1 = key;
const uint8_t* k2 = key + 32;   // <-- assumes 64-byte key
```

If a caller passes a 32-byte key (the function has no `key_len` parameter to detect this), `k2` reads 32 bytes past the buffer — out-of-bounds read.

**Fix required:** Add a `key_len` parameter and assert >= 64.

#### N-M7: `ed25519_validate_public_key` and `ed25519_validate_private_key` are weak
**File:** `libraries/libenchantcrypto/src/primitives/ed25519.cpp:99-131`

`validate_public_key` tries to verify a zero signature and only catches trivial forgeries (catches identity point only). It does not call `crypto_sign_ed25519_small_order` or `crypto_core_ed25519_is_valid_point`. `validate_private_key` only checks the seed is not all-zero. Many weak keys (small-order, mixed-order, attacker-controlled) pass.

**Fix required:** Use libsodium's `crypto_sign_ed25519_small_order` and `crypto_core_ed25519_scalar_is_canonical`.

#### N-M8: `phone_number_identity` and `incremental_mac_t` use `std::vector<uint8_t>` for secrets
**File:** `libraries/libenchantcrypto/src/protocol/phone_number_identity.cpp`, `src/api.cpp:1110-1119`

AGENTS.md §75 forbids "No secret material in `std::vector`". `phone_number_identity.cpp:25-28` uses `.clear()` (calls `SecureBuffer::clear()` which now does `sodium_memzero`, but the wrapper around `std::vector` is fragile). `enchant_incremental_mac_t.key` (`api.cpp:1112`) is `std::vector<uint8_t>`. `enchant_fingerprint_t.scannable` (`api.cpp:1107`) likewise.

**Fix required:** Use `SecureBuffer` everywhere secret material is stored.

#### N-M9: Prefix tree `verify_prefix_proof` does `index++` instead of `index /= 2`
**File:** `libraries/libenchantcrypto/src/keytrans/prefix_tree.cpp:172`

```cpp
for (const auto& sibling : proof.path) {
    ...
    index++;   // <-- should be index /= 2
}
```

Combined with N-H1, proofs produced by the same library won't verify against the same library's root.

**Fix required:** Use `index /= 2` (matches `transparency_log.cpp:97-110`).

#### N-M10: `prefix_tree.cpp` `get_prefix_proof` uses `std::sort` comparator with `sodium_memcmp` on variable-length keys
**File:** `libraries/libenchantcrypto/src/keytrans/prefix_tree.cpp:86-90, 216-222`

The comparator uses `std::min(nodes_[a].key.size(), nodes_[b].key.size())` for the comparison length. If two keys share a prefix, the comparator returns `< 0` even when one is a prefix of the other. The sort may place nodes in an order inconsistent with the tree's binary shape. Combined with N-H1, this corrupts the proof path.

**Fix required:** Use full 32-byte key comparison (or hash the keys first to a fixed length).

### LOW

#### N-L1: `noise.cpp` NoiseSymmetricState::split doesn't zero output buffers
**File:** `src/protocol/noise.cpp:128-132`

#### N-L2: `cmac.cpp` uses `empty_buffer[64]` static for NULL+0 input
**File:** `src/primitives/cmac.cpp:20-30`

The check `if (!data_ptr) { ... data_ptr = empty_buffer; actual_len = 0; }` is correct, but a caller who passes `data=NULL, data_len=1` hits the NULL check and returns `ERROR_NULL_POINTER` — the early return should compare against `data_len`.

#### N-L4: `veil_v2.cpp` parse doesn't validate recipient count
**File:** `src/veil/veil_v2.cpp:480-481`

`if (data_len < 5) return ENCHANT_VEIL_ERROR_DECRYPTION_FAILED;` is too lax.

#### N-L5: `triple_ratchet.cpp` `skipped_keys_` not zeroed on move
**File:** `src/protocol/triple_ratchet.cpp:311-324`

The move constructor moves the `std::vector` but the `MessageKey` values are not zeroed in the source. Vector's move correctly transfers ownership, but the `MessageKey::zero()` is not called on the source.

#### N-L6: `groups_v2.cpp` add_member uses XOR-OR for member_id comparison
**File:** `src/groups/groups_v2.cpp:65-71, 102-109, 134-141, 174-181`

The constant-time pattern is correct, but the loop is bounded by the data (not the input length), so it leaks membership count through timing.

#### N-L7: `noise.cpp` NoiseTransport doesn't enforce 2^64 max counter
**File:** `src/protocol/noise.cpp:345-367`

After 2^64 messages, the counter wraps to 0 and reuses the same nonce with the same key.

## 5. Wire Format Compatibility

**The libraries are intentionally incompatible.** Wire format is intentionally different — Enchant is a competitor, not a Signal reimplementation.

| Aspect | libenchantcrypto | libsignal |
|---|---|---|
| **AEAD for messages** | XChaCha20-Poly1305-IETF | AES-256-GCM |
| **AEAD for sealed sender V2** | Not implemented (V1 only) | AES-256-GCM-SIV (no nonce, one-use key) |
| **AEAD for sender key group** | AES-256-CBC + HMAC | AES-256-CBC + HMAC |
| **Serialization** | Protobuf + custom TLV | Protobuf (extensive) |
| **Message key KDF** | HKDF from chain key | HMAC from chain key |
| **PQ KEM default** | ML-KEM-768 (feature-gated) | ML-KEM-1024 (default) |
| **SPQR envelope** | Appended to envelope | Not in deployed wire (spec only) |
| **Envelope header** | `ratchet_key(32) + counter(4) + prev_counter(4) + MAC(16) + ciphertext` | `ratchet_key + counter + prev_counter + ciphertext + MAC` |
| **Server cert size** | 100 bytes (fixed) | Variable protobuf |
| **Sender cert size** | 144 bytes (fixed) | Variable protobuf |
| **Session version** | 1, 2, 3 (with explicit migration) | 3 (with PQXDH) |
| **Backup format** | TLV-style + PKCS#7 padding | Protobuf-based |
| **Device transfer** | Custom ASN.1 | Standard X.509 |
| **Storage manifest** | Custom | Protobuf |
| **MLS wire format** | Custom (not real RFC 9420) | Not adopted |
| **Group links** | Custom | Not in libsignal |
| **Username link** | AES-256-CBC + HMAC + 32-byte entropy | Same structure, different protobuf |

**Conclusion:** A message encrypted by libsignal cannot be decrypted by libenchantcrypto, and vice versa. This is by design. Even within a single library, the wire format changes between versions (e.g., Sealed Sender V1 → V2, PQXDH deployment).
