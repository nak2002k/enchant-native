### 3. Backup Forward-Secrecy Ratchet Broken

## HIGH Severity Issues (Confirmed)

### 4. Clock Type Mismatch in Session State
- **Severity:** High
- **Evidence:** `src/protocol/session_state.cpp:243` uses `std::chrono::steady_clock` for `created_at_ms`.
- **Details:**
  - `steady_clock` is self-consistent within a single process lifetime
  - Wrong choice if value is ever serialized/deserialized across process boundaries or reboots (different monotonic epoch each boot)
  - Field name `created_at_ms` is misleading — implies wall-clock Unix epoch time
  - Same pattern at `session_manager.cpp:294-296`
  - `backup_entities.hpp` uses `system_clock` for its `created_at_ms` fields (inconsistent)
- **Impact:** Session expiry checks may produce incorrect results after process restart if session state is persisted.

### 5. Blind Signatures Misleadingly Named
- **Severity:** High
- **Evidence:** `api.h:410-418` — `enchant_blind_point`/`enchant_unblind_point` are both X25519 ECDH (identical operations).
- **Details:**
  - `enchant_blind_keygen`: standard X25519 keypair generation
  - `enchant_blind_point`: X25519 DH shared secret computation
  - `enchant_unblind_point`: identical X25519 DH (same function body)
  - `enchant_zkp.hpp:14-35` sign/verify is standard Schnorr via POKSHO framework, not blind signatures
  - Proper blind schemes exist in `zkcredential/blind.hpp` (Pedersen-like) and `svr/oprfs.cpp` (OPRF) but aren't exposed through C API
- **Impact:** API naming is deceptive. Callers expecting cryptographic blinding get standard DH instead.

### 6. PQ Noise Transport Absent
- **Severity:** High
- **Evidence:** No Noise protocol implementation anywhere in the codebase.
- **Details:**
  - All PQ primitives present: ML-KEM-768/1024, X25519, ChaCha20-Poly1305, SHA-256
  - No `snow` equivalent in C++, no Noise handshake state machine
  - No `Noise_NKhfs_25519+Kyber1024_ChaChaPoly_SHA256` pattern
  - No `TransportState` for encrypted message transport after handshake
  - No Noise crypto resolver mapping primitives
  - Reference libsignal has: `NOISE_PATTERN = "Noise_NK_25519_ChaChaPoly_SHA256"` and PQ variant `Noise_NKhfs_25519+Kyber1024`
- **Impact:** Attestation and SVR server communication cannot use Noise-encrypted transport.

### 7. Replay Dedup Has Unbounded Growth
- **Severity:** High (revised from initial assessment)
- **Evidence:** `consumed_keys_` map in envelope_state.cpp grows without bound within a session.
- **Details:**
  - Two-layer dedup exists: `consumed_keys_` map (SHA256(ephemeral):counter) + `take_skipped_key()` erasure
  - `consumed_keys_` has no eviction policy, no TTL, no ack-based cleanup
  - Skipped-key store has 2000-entry cap, but `consumed_keys_` does not
  - Over very long sessions with high message volumes, this becomes a memory concern
- **Impact:** Memory leak potential in long-lived sessions.

### 8. Constant-Time Violations (3 Found)
- **Severity:** High
- **Evidence:** 3 non-constant-time comparisons on sensitive data.
- **Violations:**
  1. **HIGH** — `src/zk/zkcredential/endorsement_3hashsdhi.hpp:162-164`: Byte-by-byte loop with early break on 32-byte compressed Ristretto member key bytes. Leaks index of first differing byte via timing.
  2. **MEDIUM** — `src/groups/mls_state_machine.cpp:966`: `std::array::operator==` on 32-byte MLS identity keys (may short-circuit).
  3. **LOW** — `src/media/sanitizer.cpp:105,148`: `std::memcmp` on media data (not crypto keys, but violates coding standard).

# Comprehensive Comparison: libenchantcrypto vs libsignal

## Executive Summary

libenchantcrypto is a faithful C++ reimplementation of libsignal's cryptographic core. In raw cryptographic primitives and test volume, it is at parity or slightly ahead. In architecture, production readiness, attestation, and testing infrastructure, libsignal is significantly ahead. The comparison below covers every major subsystem.

---

## 1. Cryptographic Primitives

| Primitive | libenchantcrypto | libsignal | Verdict |
|-----------|-----------------|-----------|---------|
| **X25519 DH** | Wraps libsodium. Zero key rejection, canonical checks, low-order point rejection. | Wraps `x25519-dalek`. Torsion-free check, scalar range validation. | **Parity** — libsignal has more rigorous torsion tests |
| **Ed25519** | Wraps libsodium. Deterministic signing. Canonical signature check. | Pure Rust `curve25519-dalek` XEdDSA. Signs with X25519 key directly. | **Parity** — different approaches, both correct |
| **HMAC-SHA256/HKDF** | Wraps libsodium. Full RFC 5869 + HPKE expand_label support. | Wraps `hmac` crate. HKDF in protocol layer only. | **libenchantcrypto better** — complete HKDF with HPKE |
| **AES-GCM** | OpenSSL EVP. | Pure Rust `aes` + `ghash`. | **Parity** |
| **AES-GCM-SIV** | Hand-rolled. POLYVAL, GF multiplication. | Not implemented. | **libenchantcrypto better** |
| **AES-SIV** | Hand-rolled. CMAC-based S2V. | Not implemented. | **libenchantcrypto better** |
| **XChaCha20-Poly1305** | Wraps libsodium. | Not implemented. | **libenchantcrypto better** |
| **SHA-256/BLAKE2b** | Wraps libsodium + BoringSSL. | Wraps `sha2` + `blake2` crates. | **Parity** |
| **Ristretto255** | Wraps libsodium with C++ RAII. | Pure Rust via `curve25519-dalek`. | **Parity** — Rust types add safety |
| **Constant-Time Ops** | `sodium_memcmp`, CT select, CT compare variants (14 functions). | `subtle` crate (`ConstantTimeEq`, `Choice`). | **Parity** |
| **Secure Memory** | `SecureBuffer` with `sodium_malloc`/`sodium_memzero`, guard pages, canary. | Rust `Zeroize` trait + `memsec` crate. | **Parity** |

**Summary:** libenchantcrypto has **broader cryptographic coverage** (more AEADs, complete HKDF). libsignal has **stronger type safety** (Rust ownership) and **more rigorous test vectors** for edge cases like torsion points.
